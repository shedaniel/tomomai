# Multi-game architecture

One app serves maimai DX and CHUNITHM. Each deployment serves one game, chosen by `FRONTEND_GAME`, and every deployment shares the database, the accounts and the public API. This document says where each game concern lives, which rules keep the games apart, and what migration 0018 must preserve.

Related documents: catalog identity in [PARENT_SONG.md](PARENT_SONG.md), the CHUNITHM catalog source in [CHUNITHM_CATALOG.md](CHUNITHM_CATALOG.md), the observed CHUNITHM-NET pages in [CHUNITHM_NET.md](CHUNITHM_NET.md), and the proposal for per-game domains with shared sign-in in [plans/multi-domain.md](plans/multi-domain.md). Paths below are under `apps/main/src` unless they start with `apps/` or `packages/`.

## Where things live

- **Ids and codes.** [`lib/games/ids.ts`](../apps/main/src/lib/games/ids.ts) lists the game ids and regions. It has no imports, because drizzle-kit, `eslint.config.mjs` and the Discord command script load it directly. Each game's integer codes (difficulty, chart type, combo, sync and clear status, title type) are one table in [`packages/games/src/codes.ts`](../packages/games/src/codes.ts), shared with render and guess. A code is its key's index, so keys are only ever appended.
- **Definitions.** A game is one `GameDefinition` ([`lib/games/types.ts`](../apps/main/src/lib/games/types.ts)) in `lib/games/<game>/definition.ts`: brand, sites, capabilities and region overrides, version table, rating, recommendation targets, presentation, `/db` sections, fetch stages, login methods and the regions whose catalog source needs a player token. [`lib/games/registry.ts`](../apps/main/src/lib/games/registry.ts) lists them, and `getGame(id)` reads one. A definition imports only leaf modules (its own folder, `version-table.ts`, the codes), because a module that imports the registry would load before the definition exists.
- **Served game.** `getCurrentGame()` in [`lib/games/current.ts`](../apps/main/src/lib/games/current.ts) turns the deployment's definition and enabled regions into a serializable `FrontendGame` ([`lib/games/frontend.ts`](../apps/main/src/lib/games/frontend.ts)). `GameProvider` hands it to client components, which call `useGame()` once each, and server components call `getCurrentGame()` themselves. `isPlayerAvailable(game)` gates the dashboard and profiles. Routes that only exist for maimai call `requireFrontendGame("maimai")` first and answer 404 elsewhere.
- **Server modules.** `server/services/games/<game>/index.ts` exports the game's `GameServerModule` ([`server/services/games/types.ts`](../apps/main/src/server/services/games/types.ts)): catalog source, score source, recent play details reader and optional reserved demo profiles, whose usernames no account may take. [`server/services/games/registry.ts`](../apps/main/src/server/services/games/registry.ts) lists them. Each module imports its implementations lazily, so importing the registry stays cheap.
- **Access.** `resolveGameContext` in [`lib/games/access.ts`](../apps/main/src/lib/games/access.ts) is the one check of game, region and capability, and [`lib/games/errors.ts`](../apps/main/src/lib/games/errors.ts) gives each rejection its HTTP and tRPC status. Generic tRPC procedures build on [`server/routers/game-procedures.ts`](../apps/main/src/server/routers/game-procedures.ts). Procedures only maimai has live under `trpc.maimai` ([`server/routers/maimai/`](../apps/main/src/server/routers/maimai/)) and take no game input.
- **Fetching.** [`fetch-sessions.ts`](../apps/main/src/server/services/games/fetch-sessions.ts) admits a fetch and runs its session, [`fetch-run.ts`](../apps/main/src/server/services/games/fetch-run.ts) runs each stage, [`snapshot-persistence.ts`](../apps/main/src/server/services/games/snapshot-persistence.ts) saves the snapshot in one transaction and [`score-storage.ts`](../apps/main/src/server/services/games/score-storage.ts) writes scores and the stored rating selection. A result that arrives after the fetch deadline is never saved, and a score whose chart name is ambiguous is skipped rather than stored on an arbitrary chart. A score source may return an `enrich` step, which runs after the session completes and only logs its failures. A fetch refused before its session starts throws `FetchStartError` ([`fetch-errors.ts`](../apps/main/src/server/services/games/fetch-errors.ts)), and every transport answers it from one status table.
- **Sign-in and sites.** The token dialog offers the definition's `loginMethods` for the selected region. Token formats are in [`lib/games/token-format.ts`](../apps/main/src/lib/games/token-format.ts), and [`token-policy.ts`](../apps/main/src/server/services/games/token-policy.ts) accepts a token only for a login method of its region. Game sites are read through `openGameSite` and signed in through `openSegaSession` ([`server/services/games/sega/`](../apps/main/src/server/services/games/sega/)). Each site's origin, mobile root, gateway data and maintenance window are in its definition, read through [`lib/games/sites.ts`](../apps/main/src/lib/games/sites.ts) and [`lib/games/maintenance.ts`](../apps/main/src/lib/games/maintenance.ts). The bookmarklet's login authorization ([`lib/otp.ts`](../apps/main/src/lib/otp.ts)) signs the user, game and region.
- **Catalog.** [`server/services/catalog/`](../apps/main/src/server/services/catalog/) collects, validates, stores, publishes and revalidates every game's catalog through one pipeline. A game plugs in through the `catalog` source of its server module, implemented under `server/services/games/<game>/catalog/`.
- **Ratings.** Each game's rating math is in `lib/games/<game>/rating.ts`, reached through the definition's `rating`. [`lib/games/ranking.ts`](../apps/main/src/lib/games/ranking.ts) is the one ranking selector, and [`lib/games/recommendations.ts`](../apps/main/src/lib/games/recommendations.ts) the one recommendation engine over the definition's targets.
- **Player UI.** Generic panels are in `components/player/` and read the view types in [`lib/games/player-view.ts`](../apps/main/src/lib/games/player-view.ts). One game's UI is in `components/games/<game>/`, and pieces every game draws its own way (score hover, recent play details) are `GAME_UI` slots in [`components/games/registry.tsx`](../apps/main/src/components/games/registry.tsx). The dashboard tabs are the table in [`components/player/player-tabs.tsx`](../apps/main/src/components/player/player-tabs.tsx). Labels, colours, formats and grades come from the definition's `presentation` through [`lib/games/presentation.ts`](../apps/main/src/lib/games/presentation.ts) or `usePresentation()`, and shared components such as `ChartTypeBadge` and `ChartLevel` render it. Game site images load through `/api/image-proxy` for the hosts in each presentation's `imageProxyHosts` ([`lib/images.ts`](../apps/main/src/lib/images.ts)). Client code types tRPC payloads with [`lib/trpc-types.ts`](../apps/main/src/lib/trpc-types.ts).
- **Brand and copy.** Names, domain and artwork are the definition's `brand`, and a game without artwork is drawn with its brand title as text. Page metadata comes from `buildPageMetadata` ([`lib/seo.ts`](../apps/main/src/lib/seo.ts)), which states every page's image, because Next links a route's image file whenever a page leaves `images` out. Copy whose wording differs per game lives in `apps/main/messages/games/<game>/<locale>.json`, which [`i18n/messages.ts`](../apps/main/src/i18n/messages.ts) lays over the shared files ([messages/i18n.md](../apps/main/messages/i18n.md)).
- **Public API.** A route under `app/api/v1/games/[game]/` declares a spec with `defineGameRoute` ([`lib/api/registry.ts`](../apps/main/src/lib/api/registry.ts)) and serves it with `defineGameHandler` ([`lib/api/protect.ts`](../apps/main/src/lib/api/protect.ts)) or, for public routes, `definePublicGameHandler` ([`lib/api/route.ts`](../apps/main/src/lib/api/route.ts)). Response schemas are in [`lib/api/schemas/`](../apps/main/src/lib/api/schemas/).
- **Test fixtures.** Build a `FrontendGame` with `testGame(id, regions)` ([`test/games.ts`](../apps/main/src/test/games.ts)) and database tests with the keyed proxy in [`test/pg-proxy.ts`](../apps/main/src/test/pg-proxy.ts).

## Rules

- **Never compare the game id outside a game folder.** Check a capability, read a definition field or render a `GAME_UI` slot. [`test/game-branching.test.ts`](../apps/main/src/test/game-branching.test.ts) fails on a game id comparison anywhere except `lib/games/<game>`, `components/games/<game>`, `server/services/games/<game>` and `server/routers/<game>`.
- **Keep game folders apart.** ESLint stops a game folder from importing another game's folder, and stops `lib/games`, `components` and `hooks` from importing anything but types from `@/server`. Shared code reaches a game through the registries.
- **Scope game data at its root.** Queries filter by game on root rows only: `user_snapshots`, `user_recent_songs`, `user_albums`, `user_tokens`, `fetch_sessions`, `user_game_preferences` and catalog listings of `songs` or `parent_song`. A child row needs no game predicate, because its composite foreign key keeps it in its parent's game. That covers `snapshot_scores`, `snapshot_rankings` and `user_events` under a snapshot, `songs` or `parent_song` joined from a user row or from each other, and the catalog reference checks that find a chart's `score_data`, `user_recent_songs` and `user_albums` rows. Indexes on a child's foreign key lead with the parent id, so these lookups need no game either. The newest snapshot of a user in a region is read only through `latestSnapshot` ([`server/queries/latest-snapshot.ts`](../apps/main/src/server/queries/latest-snapshot.ts)).
- **Store codes and convert at the edge.** Queries return code rows. The old maimai string vocabulary (achievement, DX score, combo and sync names) is produced only by [`server/services/games/maimai/legacy-view.ts`](../apps/main/src/server/services/games/maimai/legacy-view.ts), for the snapshot export, render tokens and the database top songs list.
- **Name versions without regions.** Label a version with `getVersion(game, id)` ([`lib/games/versions.ts`](../apps/main/src/lib/games/versions.ts)), because a version keeps its name where it was never released. The region-aware lookups there are for gating and release timing, and `versionReleaseInstant` ([`lib/games/version-table.ts`](../apps/main/src/lib/games/version-table.ts)) is the only 07:00 JST rollover rule.
- **Readers of a snapshot's rating read its stored selection.** The API B50 scope, the Discord profile and the rating history read `snapshot_rankings`, so they agree with the rating the snapshot was saved with.
- **Visitors read through a view.** A published snapshot is read through `publicSnapshotProcedure` or `maimaiPublicSnapshotProcedure`, which call `resolvePublicSnapshotAccess` ([`server/queries/public-access.ts`](../apps/main/src/server/queries/public-access.ts)). The profile must be published and listed, the owner's privacy settings must allow the view in `PUBLIC_VIEWS` ([`lib/games/public-player.ts`](../apps/main/src/lib/games/public-player.ts)), and the game must offer the capability in the snapshot's own region. A hidden view answers NOT_FOUND, like a missing snapshot, and the player tabs hide the same views. The credit and daily play image routes resolve a visitor the same way.
- **Region choices are per game.** The dashboard region and the profile main region live in `user_game_preferences`. Read them through `gamePreference(game, key)` and write them through `saveGamePreference` ([`server/queries/game-preferences.ts`](../apps/main/src/server/queries/game-preferences.ts)). A game the user has not chosen for falls back to the account columns `user.region` and `user.profileMainRegion`, which nothing writes any more. tRPC answers the stored choice and clients clamp it with `getGameRegion`, while `/api/v1/me` and `/api/v1/me/settings` answer it clamped to the game's enabled regions. Publishing, the privacy switches, the description and the album preference stay account-wide.

## Capabilities

`GAME_CAPABILITIES` in `lib/games/types.ts` names every feature a game may offer, and each definition declares its own list. `regionCapabilityOverrides` withdraws a capability in one region, such as maimai albums in China, where a fetch neither reads albums nor asks for the album preference. Every game offers `catalog`. The served game's effective capabilities are `catalog` alone while it enables no region, and its whole list otherwise. Clients ask `supportsGameFeature(game, capability, region?)` and the server `resolveGameContext`. Both apply `offersCapability` ([`lib/games/capabilities.ts`](../apps/main/src/lib/games/capabilities.ts)), and [`lib/games/frontend.test.ts`](../apps/main/src/lib/games/frontend.test.ts) holds their answers equal. Given a region, a feature also needs that region to be enabled.

A feature only one game has, such as maimai's plates, percentiles or TomomaiAI, is a capability whose host renders the owner's component. `SINGLE_GAME_FEATURES` in the branching test pins its owner, so move the component behind a `GAME_UI` slot before a second game declares it. `/db` sections follow the same rule through the definition's `catalogSections` and `SINGLE_GAME_SECTIONS`.

## Rollout and deployment

- `FRONTEND_GAME` (`maimai` by default) picks a deployment's game at build time, and a build must start with the value it was built with. [SETUP.md](../SETUP.md#running-locally) covers running each game locally. `DEV_PORTS` in [`lib/games/frontend-config.ts`](../apps/main/src/lib/games/frontend-config.ts) must match the root `dev:<game>` scripts, which a test checks.
- `NEXT_PUBLIC_ENABLED_<GAME>_REGIONS` lists the regions whose player features a deployment enables for a game. Unset means every region the game has a site for except China. An empty value enables none: the catalog stays readable and player requests answer 422. A value that names no region of the game is logged and disables the game too. [`packages/utils/src/regions.js`](../packages/utils/src/regions.js) resolves the value for the app and for the Discord command script, and maimai still reads the legacy `NEXT_PUBLIC_ENABLED_REGIONS` while its own variable is unset. A deployment that enables only China (`isGameCnExclusive`) pins the Chinese locale and every region choice.
- Every deployment serves every game's public API, but only the game's own deployment renders its pages. Catalog writes therefore run there, other deployments answer 409, and the writer asks the deployments in `CATALOG_PEER_ORIGINS` to drop their cached copies. Each game has its own Discord update webhooks. The Discord bot serves maimai (`DISCORD_GAME` in [`lib/discord/game.ts`](../apps/main/src/lib/discord/game.ts)).

## Adding a game

1. Append its id to `CANONICAL_GAME_IDS`. It is also the `game` database enum, so the schema change needs a generated migration.
2. Add its code table to `GAME_CODES` in `packages/games/src/codes.ts`.
3. Create `lib/games/<game>/` with its definition, version table, rating, presentation, grades and recommendation targets, and add the definition to the registry. `lib/games/registry.test.ts` checks the definition's invariants.
4. Declare its recent play details in `RecentDetailsByGame` ([`lib/games/recent-details.ts`](../apps/main/src/lib/games/recent-details.ts)) and give it a `GAME_UI` entry.
5. Create `server/services/games/<game>/index.ts` with its catalog source, score source and recent details reader, and add it to `GAME_SERVER_MODULES`.
6. Add `lib/api/schemas/<game>.ts` with its `details` builders and add it to `GAME_API_DETAILS` ([`lib/api/schemas/index.ts`](../apps/main/src/lib/api/schemas/index.ts)).
7. Add its variable to `ENABLED_REGIONS_ENV` ([`lib/games/regions.ts`](../apps/main/src/lib/games/regions.ts)), a `DEV_PORTS` entry and a root `dev:<game>` script.
8. Add `apps/main/messages/games/<game>/<locale>.json` with the same keys as the other games, and its artwork under `apps/main/public/` for its brand.
9. Deploy it with `FRONTEND_GAME=<game>`, publish its catalog there, list its origin in the other deployments' `CATALOG_PEER_ORIGINS`, and set its Discord update webhooks.

Each registry above is typed over every game id, so a missing step fails typecheck, and the ESLint boundaries derive their game list from `CANONICAL_GAME_IDS`.

## Public API contract

- Game data lives under `/api/v1/games/{game}`, with canonical ids only, and every game response carries `game`. `/api/v1/me`, `/me/settings`, `/me/scopes` and `/ok` are global. A route declares its capability, and the reference and the OpenAPI document list only the games that offer it.
- `GET /api/v1/games/{game}/codes` is public and serves the game's code table. Every code field in a schema points at it.
- A field only one game has goes in a `details` object named by its `game`. `GAME_API_DETAILS` requires each game's builders.
- Errors are `{ error, code? }`. The codes any route may answer are `API_ERROR_CODES` ([`lib/api/error-codes.ts`](../apps/main/src/lib/api/error-codes.ts)), built from the game error table, and a route lists its own refusals in its spec's `errors`, such as the fetch refusals from `FETCH_START_ERROR_STATUS` ([`lib/games/fetch-error-codes.ts`](../apps/main/src/lib/games/fetch-error-codes.ts)). The OpenAPI document and the errors guide render both.
- The roots from before the namespace (`/api/v1/songs`, `/api/v1/recents` and the others) answer 410 with the maimai `location` ([`app/api/v1/[...legacy]/route.ts`](<../apps/main/src/app/api/v1/[...legacy]/route.ts>)). Any other unknown `/api/v1` path answers a JSON 404.
- The catalog is published to R2 under `catalog/v2/{game}` ([`lib/api/catalog-location.ts`](../apps/main/src/lib/api/catalog-location.ts)) and the API redirects to it. Bump `CATALOG_FORMAT_VERSION` there when the published JSON changes shape. Catalog cache tags come from `catalogTags(game)` ([`lib/cache-tags.ts`](../apps/main/src/lib/cache-tags.ts)).
- Integrators read breaking changes in the [changelog guide](../apps/main/content/developer/guides/changelog.mdx).

## Migration 0018

Migration 0018 is the one migration after upstream 0017. Its generated diff is customised to keep every row:

- It runs in one transaction and locks the affected tables. Before converting anything it checks that the legacy maimai enums keep the label order the code conversion relies on, and that every `snapshot_b50` rank lies in 0 to 49. A failed guard aborts the cutover, and the fix is the data, not the guard.
- It sets `game = 'maimai'` on every existing row, renames the score and recent metric columns in place (for example the achievement column to `scoreValue`, `dxScore` to `secondaryScore` and `maxDxScore` to `maxSecondaryScore`), and converts chart, status and title strings to codes in the verified enum order. Temporary `game` defaults are removed, so every write names its game.
- Every parent, song, snapshot and score id is kept. The game-matching composite foreign keys are added after the unique constraints they reference.
- `snapshot_b50` ranks 0 to 14 become the new bucket and ranks 15 to 49 the old bucket of `snapshot_rankings`, with bucket-relative ranks.
- Both known percentile materialized views are dropped, with restrictive drops, before any column type changes.
- `user_snapshots_maimai_fields` and `user_recent_songs_maimai_fields` keep the columns maimai rows always filled non-null. Child foreign key indexes lead with the parent id. Only `songs` and `user_recent_songs` gain `metadata`.
- `user_game_preferences` is created and filled with every user's region and main region as their maimai choice.

The checked-in artifact predates the current schema and is regenerated before release. The new artifact renames `maxDxScore` to `maxSecondaryScore`, adds both check constraints, the reshaped indexes and `user_game_preferences` with its backfill, leaves `metadata` off `parent_song`, `user_snapshots`, `user_events` and `user_albums`, and drops the duplicate identity and post-backfill checks, which the unique constraints and foreign keys already guarantee. Until then [`apps/main/scripts/check-multi-game-migration.mjs`](../apps/main/scripts/check-multi-game-migration.mjs) checks the view drop order of the checked-in artifact.

Cutover:

1. Back up the database and open a write maintenance window. The migration locks the large score tables and rebuilds indexes, so estimate its duration and disk headroom on the real dataset.
2. Apply 0018 in one transaction after 0017 through the authorized deployment mechanism.
3. Deploy each game's app with render and guess. On each game's deployment, publish its catalog with `POST /api/admin/catalog/publish?game=<game>` before reopening traffic.
4. Run the percentile refresh job, which recreates the maimai view. Until then percentile reads return no bands.
5. Purge CDN copies of the old `/api/v1` paths and redirects. Check a maimai fetch, profile image and last credit, and the CHUNITHM catalog and one CHUNITHM profile.

Rolling back only the application is not supported. Restore the database together with the matching old application.
